1. Introduction

This system is a FastAPI-based web application that simulates both
vulnerable and secure API environments. It demonstrates backend security
risks such as SQL injection, request flooding, and resource exhaustion,
while also implementing defenses and monitoring mechanisms.

The system integrates PostgreSQL for data persistence and optionally
uses an LLM-based analysis layer to classify and explain threats.

2. System Overview

The system provides API-based services accessed via HTTP requests.
Each request is processed through a FastAPI backend that routes traffic
to service logic and database queries.

The system supports:

- Service operations (query execution and monitored request storage)
- Vulnerable endpoints (simulated insecure behavior)
- Security monitoring middleware
- Defensive security controls
- Optional LLM-based threat analysis

3. Functional Requirements
3.1 Core API Services
The system shall:

- Expose REST API endpoints using FastAPI
- Execute predefined SQL queries for monitored request records
- Return structured JSON and HTML responses
- Provide a system health check endpoint

3.2 Vulnerable Simulation Layer
The system shall:

- Include unsafe query execution modes
- Simulate SQL injection vulnerabilities
- Allow recursive or heavy request endpoints
- Demonstrate resource exhaustion scenarios
- Vulnerable routes are disabled by default and enabled via the ENABLE_VULN_SIMULATION environment variable.

3.3 Monitoring Layer
The system shall:

- Detect and label common anomaly types: SQL Injection, XSS, Path Traversal, Command Injection, Recursive API Abuse, and Flood Attack.
- Log request metadata (IP, payload, frequency)
- Detect SQL injection patterns in request bodies and parameters
- Detect XSS (cross-site scripting) attempts
- Detect path traversal attacks
- Detect command injection attempts
- Detect recursive API abuse
- Detect flood attacks via payload size analysis
- Avoid storing noisy browser page loads and dashboard polling as security events.

3.4 Defense Layer
The system shall:

- Validate inputs using Pydantic models
- Use parameterized SQL queries
- Apply rate limiting on endpoints
- Log and flag detected threats for analysis
- Return a defense response with action, severity, rule, reason, and recommendation.
- Vulnerable simulation endpoints intentionally bypass safety controls for educational demonstration.

3.5 Logging System
The system shall:

- Store monitored API and simulation requests in PostgreSQL
- Track normal and attack events
- Support analysis of attack patterns
- Provide timeline-ready request data using stored creation timestamps.

4. Non-Functional Requirements
- System shall handle concurrent API requests
- Response time should remain under acceptable limits
- Monitored request records must be persistent in PostgreSQL
- Security checks must not block normal usage

5. LLM + RAG INTEGRATION DESIGN

The system optionally integrates an LLM (Large Language Model) to
analyze API requests and detect potential security threats using a
Retrieval-Augmented Generation (RAG) approach.

5.1 RAG Architecture

Instead of training a model, the system retrieves relevant context
from stored request records and feeds it to the LLM.

Two detection paths:
 
Path 1 (Monitored API/simulation requests):
  Request → Middleware → Rule-based detection → Store request in PostgreSQL
 
Path 2 (/api/analyze only):
  User submits payload → Rule-based detection
      → Retrieve similar past events from PostgreSQL (RAG)
      → Send payload + context to LLM
      → Defense response + optional LLM classification and explanation
      → Response returned + stored

Flow Diagram (Logical)-for analyze endpoint only.
API Request
     ↓
FastAPI Middleware
     ↓
Request record stored in PostgreSQL
     ↓
Retrieve similar past events (RAG step)
     ↓
Send:
  - current request
  - retrieved request records
  - system rules
     ↓

     ↓
Threat classification + explanation
     ↓
Response returned + stored

5.2 What is stored for retrieval:

- Previous requests from the same IP address
- Requests with similar payload content (text-based matching)
- Associated anomaly classifications from past detections
- Request metadata (endpoint, method, timestamp)

5.3 The LLM is used to:

- classify requests as safe or an attack
- Provide natural language explanations of threat assessments
- Augment rule-based detection with contextual AI analysis

Implementation notes:

- `security_system/security.py` contains local anomaly detection and defense response mapping.
- `security_system/services.py` records analyzed requests, stores anomalies, calls optional LLM analysis, and builds dashboard metrics.
- `security_system/middleware.py` performs session tracking, rate limiting, and noise-filtered monitoring.
- `security_system/llm.py` retrieves previous request records from PostgreSQL for optional RAG-style context.
- `security_system/main.py` provides the browser demo pages for analysis, health checking, API documentation, and dashboard visualization.
